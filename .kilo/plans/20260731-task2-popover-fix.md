## 4. Quality Issues

### 4.1 High-priority: redundant dual output surface

Declaring `shown = output<void>()` and `hidden = output<void>()` **and** subscribing to `NgbPopover.shown`/`hidden` creates two separate output streams on the host element: the component-level `OutputEmitterRef` and the directive's `EventEmitter`. The implementation currently emits into the component-level output, which works for tests, but it violates the spec and means the directive's native outputs are not being forwarded through `hostDirectives` as intended.

### 4.2 High-priority: input forwarding timing

Setting directive inputs via `effect()` is asynchronous. The underlying `NgbPopover` reads inputs (e.g., `triggers`) during its own `ngOnInit` before the effect has necessarily run. This can lead to:

- A brief mismatch between the declared inputs and the directive's observed values.
- The `triggers` default being used for the initial trigger registration instead of the consumer-provided value.
- The need to keep the wrapper's own `input()` fields *and* assign them to directive properties, which is unnecessary boilerplate.

`hostDirectives` input forwarding is synchronous and uses Angular's standard input binding, avoiding this class of timing issues.

### 4.3 Medium-priority: incorrect JSDoc rationale

The JSDoc contains the unsupported claim:

> "Angular's `hostDirectives` input/output forwarding does not reliably react to later input changes."

There is no evidence in the codebase or the plan that this is true. `hostDirectives` forwarding is exactly the mechanism the plan chose for this component. The comment should be replaced with the correct rationale.

### 4.4 Minor: unused imports after fix

After switching to `hostDirectives` forwarding, `effect` and `output` will no longer be used in the component file and must be removed.

### 4.5 Minor: arrow SCSS correctness

The theme file matches the plan exactly. The per-placement arrow selectors are logically paired (`::before` vs `::after`) and use the same token for both border and fill. This is a possible visual issue (arrow fill vs arrow border may not distinguish correctly on every placement), but it is not a plan deviation. The implementation plan should be followed; if visual QA later finds arrow rendering problems, a separate theme-only fix can be made.

### 4.6 Accessibility

- No wrapper-level ARIA attributes are added; the spec accepts relying on `NgbPopover`.
- Projected trigger must be focusable — this is documented in the JSDoc and spec.
- `disabled` prevents opening via `disablePopover` — correct.

## 5. Comparison with CbaDropdown

`CbaDropdown` is forced to use manual wiring because `NgbDropdown` needs a `ContentChild(NgbDropdownMenu)` query that cannot cross the component view boundary, so the wrapper has to:

1. Use `hostDirectives: [NgbDropdown]`.
2. Manually set `placement` via `effect()`.
3. Manually subscribe to `openChange`.
4. Use `ViewChild(NgbDropdownMenu)` and the private `_menu` linking hack.

`CbaPopover` does **not** need any `ViewChild`/`_menu` workaround (correctly avoided). However, the implementation still copied the manual `effect()` and output-subscription pattern from `CbaDropdown`, even though `NgbPopover` has no projected-content queries and can be forwarded cleanly. The popover implementation should therefore be **simpler** than the dropdown implementation, but currently it is not.

**Expected cleaner state:** `CbaPopover` uses `hostDirectives` for input/output forwarding and only injects `NgbPopover` to set `popoverClass` and `container`.

### 6.3 Exact changes for `cba-popover.component.spec.ts`

The existing output test is:

```ts
it('re-emits NgbPopover shown and hidden through the wrapper outputs', () => {
  const fixture = TestBed.createComponent(PopoverHost);
  fixture.detectChanges();
  const popover = fixture.debugElement.query(By.directive(CbaPopoverComponent)).injector.get(NgbPopover);

  popover.shown.emit();
  expect(fixture.componentInstance.onShown).toHaveBeenCalled();

  popover.hidden.emit();
  expect(fixture.componentInstance.onHidden).toHaveBeenCalled();
});
```

This test should still pass after the fix because `hostDirectives` output forwarding re-emits the directive's `shown`/`hidden` events on the host element. However, to make the test intent explicit, add a brief comment and, if desired, assert that the component class itself does **not** own a separate output by importing `CbaPopoverComponent` and checking it has no `OutputEmitterRef` fields named `shown`/`hidden`.

Recommended change:

```ts
it('re-emits NgbPopover shown and hidden through the host element outputs', () => {
  const fixture = TestBed.createComponent(PopoverHost);
  fixture.detectChanges();
  const popover = fixture.debugElement.query(By.directive(CbaPopoverComponent)).injector.get(NgbPopover);

  // With hostDirectives output forwarding, the directive's events surface
  // on <cba-popover> as (shown) and (hidden).
  popover.shown.emit();
  expect(fixture.componentInstance.onShown).toHaveBeenCalled();

  popover.hidden.emit();
  expect(fixture.componentInstance.onHidden).toHaveBeenCalled();
});
```

All other tests remain unchanged.
