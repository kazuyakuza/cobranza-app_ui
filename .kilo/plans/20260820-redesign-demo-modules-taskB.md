## ⚠️ SPEC CONTRADICTION RESOLUTION (READ BEFORE IMPLEMENTING)

The front-end spec contains an **internal contradiction** between its own sections. The implementer MUST follow the resolution below, NOT the spec's literal section 4/5 text.

### The contradiction

- Spec §3 says: replace ONLY the "New customer" module's `<div class="demo-actions">…</div>` and the "Payment schedule" module's `<p class="cba-text-body">…</p>`. It does **NOT** mention the "Export data" module.
- The current `demo-workspace.component.html` (verified) renders a **third** `demo-actions` block inside the "Export data" module:

  ```html
  <demo-module-card title="Export data" ...>
    <div class="demo-actions">
      <cba-button variant="ghost" [icon]="faDownload">Export CSV</cba-button>
    </div>
  </demo-module-card>
  ```

- Yet spec §4 says "Remove `CbaButtonComponent` import (no longer used directly in this file)" and shows a final TS with **no** `CbaButtonComponent` and only `faDownload` remaining.
- And spec §5 says "Remove the now-unused `.demo-actions` block" from the SCSS.

If the "Export data" module keeps its `<cba-button [icon]="faDownload">` (per §3) while `CbaButtonComponent` is removed from imports (per §4) and `.demo-actions` is removed from SCSS (per §5), **`npm run build:demo` fails**: unknown element `cba-button` + unknown class usage.

### Resolution (authoritative for this plan)

The TODO file is the TOP PRIORITY and scopes Task Group B to **only** the "New customer" and "Payment schedule" modules. The "Export data" module is **out of scope** and MUST be left untouched. Therefore this plan **diverges from spec §4/§5** as follows:

1. **KEEP** `CbaButtonComponent` in `demo-workspace.component.ts` imports (still used by the untouched "Export data" module).
2. **KEEP** `faDownload` in `demo-workspace.component.ts` (still used by "Export data").
3. **KEEP** the `.demo-actions` block in `demo-workspace.component.scss` (still used by "Export data").
4. **REMOVE** only `faPlus` and `faRefresh` from `demo-workspace.component.ts` (they were used only by the old "New customer" buttons, which are replaced by `<demo-customer-form />`).

This is the only interpretation that (a) matches the TODO scope, (b) keeps `npm run build:demo` green, and (c) introduces no new scope. The Planner/user will review this deviation at plan approval.

### Step 4 — Create `demo-payment-schedule` component TS

```ts
import { ChangeDetectionStrategy, Component } from '@angular/core';
import { CbaBadgeComponent } from '@cobranza-apps/ui';

/** One scheduled payment row shown under the calendar. */
interface DemoPayment {
  readonly customer: string;
  readonly amount: string;
  readonly status: 'pending' | 'paid';
}

/**
 * Demo-only payment schedule view. Shows a visual September 2026 calendar
 * with the 15th highlighted, plus a list of hard-coded payments for that day.
 *
 * **NOT part of the public library API.**
 */
@Component({
  selector: 'demo-payment-schedule',
  standalone: true,
  imports: [CbaBadgeComponent],
  changeDetection: ChangeDetectionStrategy.OnPush,
  templateUrl: './demo-payment-schedule.component.html',
  styleUrl: './demo-payment-schedule.component.scss',
})
export class DemoPaymentScheduleComponent {
  protected readonly monthYear = 'September 2026';
  protected readonly selectedDate = '2026-09-15';
  protected readonly days: readonly number[] = Array.from({ length: 30 }, (_, index) => index + 1);
  protected readonly payments: readonly DemoPayment[] = [
    { customer: 'Comercial del Sur S.A.', amount: '$ 625,000', status: 'pending' },
    { customer: 'Distribuidora Norte', amount: '$ 480,000', status: 'pending' },
    { customer: 'Tecnología Andina', amount: '$ 0', status: 'paid' },
  ];
}
```

Note: `DemoPayment` interface is intentionally NOT exported (demo-only, no consumers). Keeping it file-private satisfies the prefer-private-members rule.
