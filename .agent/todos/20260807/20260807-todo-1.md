# Phase 10 — Theme Hardening (pre–real MFEs)

Library: `@cobranza-apps/ui`  
Context: Theme identity is good. With many modules on screen the UI still reads as one large beige mass. Borders and selection language are weak. Before building real MFEs, harden surfaces, borders, interaction/selection states, form states, and a minimal type scale — without changing the `Minimal Yet Warm` identity.

## Objective

Make `Minimal Yet Warm` strong enough to support:

> Shell + 50%/100% modules + fullscreen + navigation + tables + forms + dialogs + status

when many modules share the workspace at once.

This phase is tokens + rules + light component wiring. No new business components.

## Design constraints

- Keep `Minimal Yet Warm` (warm sand/cream/taupe + controlled coral).
- Do not rename existing `--cba-*` tokens unless adding new ones listed below.
- Coral stays accent-only (warning / danger / focus emphasis) — not primary CTA fills, not large backgrounds.
- Primary accent remains warm taupe (`--cba-accent-primary`).
- Border = primary separation; shadow = secondary depth (do not invert this).
- Desktop-only; Spanish UI copy rules unchanged.
- Agent may tune hex values; acceptance is visual hierarchy + state clarity under multi-module density.

## Current baseline (approx. after Phase 9)

```text
canvas   --cba-bg-primary    ~ #C5BFAE
panel    --cba-bg-secondary  ~ #E6DDC6
elevated --cba-bg-elevated   ~ #FBF7ED
inset    --cba-bg-tertiary   ~ #D8C3A5
```

Concept is correct (`canvas → panel → elevated`, inset recessed). Multi-module screens still feel too homogeneous.

## Tasks

### 1. Surface differentiation (especially canvas ↔ panel)

- [ ] Increase canvas ↔ panel separation so modules read as cards on a desk, not beige-on-beige.
- [ ] Keep elevated near-cream / near-white so module headers and floating chrome stay distinct from panel body.
- [ ] Keep inset clearly different from panel (table headers, wells, module footer).
- [ ] Validate in `docs/theme-preview.html` and mentally against multi-module Shell density (2–4 modules visible).
- [ ] Update token comments in `_variables.scss` with the final roles.

Suggested direction (not rigid):

- Canvas: slightly darker / more taupe-sand  
- Panel: slightly clearer / lighter than canvas  
- Elevated: almost white cream  
- Inset: keep sand family but ensure Δ vs panel is obvious  

Do not abandon warm neutrals for cool gray or pure white SaaS.

### 2. Border system as a first-class tool

Make the three border levels deliberately different and document usage:

| Token | Intended use |
| ------- | ---------------- |
| `--cba-border-subtle` | Internal separators only (row lines, soft dividers) |
| `--cba-border-default` | Structural edges (module frame, cards, inputs) |
| `--cba-border-strong` | Important chrome / interactive outlines (footer pills, icon buttons, emphasis) |

- [ ] Retune hex values so subtle ≠ default ≠ strong on cream/sand.
- [ ] Prefer border for primary module separation; keep shadows secondary.
- [ ] Audit `ModuleContainer` / `ModuleHeader` / footer-related examples: structural edges should not rely only on `border-subtle` + tiny shadow.
- [ ] Document border roles in `THEME.md` + `CONSUMER_GUIDE.md`.

### 3. Explicit selected language

`--cba-hover` / `--cba-active` are not enough. Selection is critical for footer, tables, nav, modules.

- [ ] Add tokens (names may be refined, but intent must exist):

```scss
--cba-selected-bg
--cba-selected-border
--cba-selected-text
--cba-selected-hover
```

- [ ] Define semantics: selected ≠ pressed (active) ≠ focus.
- [ ] Document expected use:
  - footer section pill selected
  - nav / tab selected
  - table row selected
  - dropdown option selected
  - filter chip active
  - module “focused” chrome
- [ ] Apply selected tokens at least where lib owns the control (e.g. document pattern for pills; wire dropdown option if thin wrapper allows).
- [ ] Update theme-preview with a Selected sample row (pill + fake table row + nav item).

### 4. Form & control state matrix

Define and implement consistent visual semantics (tokens and/or shared form-field styles):

| State | Required |
| ------- | ---------- |
| default | yes |
| hover | where interactive |
| focus-visible | yes (use focus-ring) |
| disabled | yes |
| readonly | yes (distinct from disabled if possible) |
| invalid | yes |
| valid | yes |

- [ ] Add tokens if needed, e.g.:

```scss
--cba-state-invalid-border
--cba-state-invalid-text
--cba-state-valid-border
--cba-state-valid-text
--cba-state-disabled-bg
--cba-state-disabled-text
```

(Reuse accent danger/success where appropriate instead of inventing parallel reds/greens.)

- [ ] Wire `CbaInput` / `CbaSelect` / `CbaDatepicker` (and shared form-field) to these states via inputs or CSS classes already in the API — no validation engine.
- [ ] Document the matrix in new form-field /docs, and link it in related docs and README.
- [ ] Add preview samples: input default / focus / disabled / readonly / invalid.

### 5. Focus ring stress test

Keep coral-tinted focus ring direction unless it fails contrast on a critical surface.

- [ ] Verify focus-visible on: canvas, panel, elevated, inset, taupe primary button, danger, success, ghost, icon button, text input.
- [ ] Adjust ring alpha/spread only if failures appear.
- [ ] Document: MFEs must use lib focus (mixin / components), not one-off outlines.

### 6. Minimal typography scale

Base stays Inter / 14px / 1.5. Add an explicit scale as tokens or documented classes (implementation can be CSS variables + utility classes):

```text
display     ~ 20 / 24
heading-lg  ~ 18 / 22
heading-md  ~ 16 / 20
body        ~ 14 / 21   (default)
small       ~ 13 / 18
caption     ~ 12 / 16
```

- [ ] Expose as `--cba-font-size-*` + `--cba-line-height-*` (and optional `.cba-text-display` etc.).
- [ ] Map usage guidance:
  - module title → heading-md or heading-lg
  - section title → heading-md
  - table header → small/semibold
  - body → body
  - metadata / hints → caption or muted small
- [ ] Do not redesign every component typography in this phase; define scale + apply to ModuleHeader title + document consumer usage.

### 7. Radius rules

Existing: sm 6 / md 10 / lg 14.

- [ ] Document and enforce:

```text
lg  → modules / large containers
md  → cards / controls
sm  → badges / small controls
pill → nav pills / tags only
```

- [ ] Avoid arbitrary new radii in components.
- [ ] Document in `THEME.md` + `CONSUMER_GUIDE.md`.

### 8. Shadow rules

- [ ] Keep warm-tinted shadows.
- [ ] Document: border primary, shadow secondary.
- [ ] Under multi-module density, prefer clearer borders over heavier shadows.
- [ ] Only increase shadow if canvas↔panel still fails after border/surface passes.

### 9. Table state patterns (tokens + docs; full table component still out of scope)

Document (and preview if easy):

```text
row default
row hover
row selected
row disabled (optional)
```

- [ ] Use `--cba-hover`, `--cba-selected-*`, muted text as building blocks.
- [ ] Consumer guide: thead = inset; body rows = panel; selected row = selected tokens.

### 10. Navigation / footer state patterns

- [ ] Document normal / hover / selected / disabled for footer section pills and similar nav chips.
- [ ] Ensure selected is stronger than the weak popover selection in current Shell captures (token-level; Shell applies).

### 11. Semantic status patterns

- [ ] Document badge/inline status recipes:
  - success → green
  - warning → soft coral
  - danger → deeper red
  - info → steel
  - neutral → taupe/gray
- [ ] Keep warning vs danger distinguishable (color + label/icon guidance; strengthen danger hex only if still ambiguous after contrast checks).

### 12. replace ModuleHeaderComponent icons & order

- drag icon to `up-down-left-right`
- size toggle (50% <-> 100%): `arrows-left-right-to-line` and `arrows-left-right`
- fullscreen: `window-maximize`
- the icons order must be:
  - drag
  - collapse/expand
  - size toggle
  - fullscreen
  - remove

## Acceptance criteria

| # | Criterion |
| --- | ----------- |
| 1 | Multi-module layout no longer reads as a single beige slab; canvas↔panel is obvious. |
| 2 | `border-subtle` / `default` / `strong` are visibly distinct and documented by role. |
| 3 | Selected state tokens exist and are demoed (pill + row at minimum). |
| 4 | Form states default / focus / disabled / readonly / invalid are defined and shown in preview or components. |
| 5 | Focus ring verified on major surfaces and button variants. |
| 6 | Typography scale tokens (or utilities) exist with usage guidance. |
| 7 | Radius + shadow rules documented; border remains primary separator. |
| 8 | Consumer guide updated; build succeeds; `Minimal Yet Warm` identity preserved. |

## Explicitly out of scope

- Building real MFE business screens  
- Advanced `mfe-table` component  
- Shell DnD / empty-slot behavior  
- New theme families or dark mode  
- Expanding coral into primary CTAs  
- Mobile layout  

## After this phase

Theme is ready as a platform foundation for real MFEs. Further work is product UI on top of tokens + consumer guide — not another full palette reset unless hierarchy still fails after this hardening.
