# Library fix: make `@use '@cobranza-apps/ui/theme';` resolvable by Angular dev-server

**Status:** Open — for `@cobranza-apps/ui` maintainers. Supersedes `.agent\todos\20260812\20260812-todo-2-DONE.md`.

**Problem:** `@use '@cobranza-apps/ui/theme';` fails in the Angular dev-server (`ng serve`) because Angular's custom Sass importer does not resolve the specifier the way standard Dart Sass does.

## Why the 0.15.2 `theme/_index.scss` fix did not work

Adding `theme/_index.scss` relied on the assumption that Dart Sass would perform directory-index resolution on the path returned by Angular's `findFileUrl` importer. **This is incorrect.**

Sass's `findFileUrl` importer contract requires the returned URL to point to an **actual file** (with extension). Directory-index resolution (`_index.scss` lookup inside a directory) is a feature of:

- Relative URLs in `@use`/`@import` chains
- `loadPaths` (`includePaths`) resolution

It is **NOT** applied to URLs returned from `findFileUrl` importers. When Angular returns `file://<pkgRoot>/theme` (a directory URL), Dart Sass attempts to load it as a file with that literal name; when that fails, it does NOT fall through to `<pkgRoot>/theme/_index.scss`.

## Why `ng build` works but `ng serve` doesn't

`ng build` uses esbuild with conditions `['style', 'sass', ...]`. esbuild resolves the library's `exports['./theme']['sass']` → `./theme/theme.scss`, and Sass loads that file directly.

`ng serve` uses Vite's dev-server with conditions `['es2020', 'browser', 'module', 'main']` — no `sass`/`style` conditions. The package `exports` lookup fails, so Angular falls back to joining `<pkg-root>/theme` and returning a directory URL → fail.

## Required library fix: add a file literally named `theme` (no extension)

Add `node_modules/@cobranza-apps/ui/theme` (a file with **no extension**) at the package root. Content:

```scss
// node_modules/@cobranza-apps/ui/theme
@forward './theme/theme.scss';
```

Angular's importer joins the specifier to `node_modules/@cobranza-apps/ui/theme` and returns that exact path as a `file://` URL to Sass. Sass loads it directly (it does not need a `.scss` extension when loaded via an importer URL). The `@forward` then resolves to the real entry file.

**Why this works:**

- The file exists at the exact literal path Angular constructs (`<pkgRoot>/theme`).
- No package-export conditions are needed.
- No esbuild/Vite condition differences.
- Works in both `ng build` and `ng serve`.

## Alternative: change the consumer-facing API

Document that consumers must use `@use '@cobranza-apps/ui/theme.scss';` (with the `.scss` extension). The `theme.scss` shim already exists at the package root from 0.15.1. Angular's literal path resolution finds it directly. However, this forces all consumers to change their imports.

## Acceptance criteria

- [ ] `ng serve` in a consumer project (no `stylePreprocessorOptions.includePaths`, `@use '@cobranza-apps/ui/theme';` in `styles.scss`) starts without `Can't find stylesheet to import`.
- [ ] `ng build` continues to compile successfully.
- [ ] The existing `exports["./theme"]` map is preserved (backward compatibility).

## Verification steps for the library

1. Add `theme` (no extension) at the package root with `@forward './theme/theme.scss';`.
2. Publish the library (or test locally via `npm link` / file dependency).
3. In a test Angular project:
   - Remove `stylePreprocessorOptions.includePaths` from `angular.json`.
   - Use `@use '@cobranza-apps/ui/theme';` in `styles.scss`.
   - Run `ng serve` → must start without error.
   - Run `ng build` → must complete without error.

## Context for consumer projects

The Shell (`cobranza-app/front/shell`) uses `@use '@cobranza-apps/ui/theme';` in `src/styles.scss`. `ng build` works; `ng serve` is broken. The Shell intentionally did **NOT** restore the `stylePreprocessorOptions.includePaths` workaround and is waiting for this library fix. Once the library fix ships, the Shell just needs to re-verify `ng serve`.
