# Fix @cobranza-apps/ui theme import for Angular dev-server compatibility

**Problem:** `@use '@cobranza-apps/ui/theme';` fails in `ng serve` (dev-server) because Angular's Sass importer does not resolve the library's `exports["./theme"]` package-export condition.

**Where it fails:**

- `ng serve` via `@angular/build:dev-server` (wrapped by `@angular-architects/native-federation:build`) → `Can't find stylesheet to import`
- `ng build` (production/development esbuild path via native-federation builder) → passes

**Root cause (verified):**
Angular's internal Sass importer (`@angular/build/src/tools/esbuild/stylesheets/sass-language.js`) resolves package imports by:

1. Trying literal file resolution
2. Parsing the specifier into `packageName` + `pathSegments`, resolving `<packageName>/package.json` to find the package root, then joining `<packageRoot>/<rest>` directly
3. **It does NOT honor the `sass` / `style` / `default` conditions in `package.json` `exports`.**

For `@cobranza-apps/ui/theme`, the Angular importer looks for `node_modules/@cobranza-apps/ui/theme.scss` or `node_modules/@cobranza-apps/ui/theme/index.scss` (or `_index.scss`) — neither exists. The actual file is at `node_modules/@cobranza-apps/ui/theme/theme.scss`, and the library's `package.json` exposes it via:

```json
"exports": {
  "./theme": {
    "sass": "./theme/theme.scss",
    "style": "./theme/theme.scss",
    "default": "./theme/theme.scss"
  }
}
```

Angular ignores this `exports` map entirely.

## Required fix in @cobranza-apps/ui

The library must make the theme importable via a path that Angular's bare-bones Sass resolver can find without package-export conditions.

### Option A (recommended): Add a re-export file at the package root

Create `theme.scss` at the package root that forwards the real theme:

```scss
// node_modules/@cobranza-apps/ui/theme.scss
@forward './theme/theme.scss';
```

This makes `@use '@cobranza-apps/ui/theme';` resolvable by Angular's importer as `node_modules/@cobranza-apps/ui/theme.scss`, which then forwards to the real file.

**Pros:**

- Works with ALL Angular versions and build modes (dev-server, esbuild, webpack)
- No changes needed in consumer projects
- Removes the need for `stylePreprocessorOptions.includePaths` workaround entirely
- Backward-compatible with existing `exports["./theme"]` map

**Cons:**

- Adds one small re-export file to the package root

### Option B: Expand exports to include a direct root-level mapping

Add an additional export that maps `./theme.scss` directly:

```json
"exports": {
  "./theme": {
    "sass": "./theme/theme.scss",
    "style": "./theme/theme.scss",
    "default": "./theme/theme.scss"
  },
  "./theme.scss": "./theme/theme.scss"
}
```

This would let Angular resolve `node_modules/@cobranza-apps/ui/theme.scss` via the direct export, but Angular still wouldn't use the `exports` map — it would just find the file directly if it exists. So Option A is functionally equivalent and simpler.

### Option C: Add `theme/_index.scss` partial

Create `node_modules/@cobranza-apps/ui/theme/_index.scss` (or `theme/_index.scss` and `theme/index.scss`). Sass partial resolution might find `_index.scss` when importing `@cobranza-apps/ui/theme`. However, Angular's importer does not use standard Sass partial resolution for package imports — it uses its own custom resolver. This option is **NOT reliable** and should be avoided.

## Context for consumer projects

The Shell project (`cobranza-app/front/shell`) currently has a `stylePreprocessorOptions.includePaths` workaround in `angular.json` that points to `node_modules/@cobranza-apps/ui/theme`, plus `@use 'theme';` in `src/styles.scss`. This workaround was introduced because the Angular dev-server cannot resolve the library's `exports["./theme"]` map. Once the library fix is released, the Shell can remove the workaround and switch to the canonical `@use '@cobranza-apps/ui/theme';` import.
